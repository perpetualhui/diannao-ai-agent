# 店脑 · 多用户与服务器部署

日期：2026-11-07｜状态：多用户改造已在本机完成并验证；服务器部署方案待执行

## 一、结论先说

**能支持多用户，而且现在已经在本机跑起来了。**

但要把「多用户」拆成两层看：

| 层 | 原来 | 现在 |
|---|---|---|
| 店脑业务 API | 本来就支持多租户（tenant_id + 角色），但只有测试账号 | 不改，直接复用 |
| 微信接入层 | **所有微信用户共用一个店脑账号**（staff-a） | 已改为每个微信 sender 绑定自己的账号，租户/角色隔离 |
| 对话上下文 | 所有微信用户共享一个 session | 已改为 `per-account-channel-peer`，每人独立上下文 |

## 二、已完成的多用户改造

### 2.1 用户绑定表

`adapters/wechat/users.json`：

```json
{
  "users": [
    { "sender_id": "wxid-staff-luo", "login_name": "staff-a", "password": "demo", "label": "罗店员（A店 staff）" },
    { "sender_id": "wxid-owner-zhou", "login_name": "manager-a", "password": "demo", "label": "周店长（A店 owner）" },
    { "sender_id": "wxid-staff-b", "login_name": "staff-b", "password": "demo", "label": "B店店员" }
  ]
}
```

网关按 `sender_id` 查表，用对应用号登录店脑 API：
- 每个 sender 独立 token，30 分钟缓存，互不串用
- 未绑定 sender 一律拒绝（fail-closed）
- 旧的单账号环境变量模式仍兼容

### 2.2 实测隔离结果

| 微信用户 | 查询「尾号 1234」 | 结果 |
|---|---|---|
| 罗店员（A 店 staff） | 张女士（A 店） | ✅ 看到 A 店数据 |
| B 店店员 | 张先生（B 店） | ✅ 看到 B 店数据，与 A 店互不可见 |
| 未绑定用户 | — | ✅ 拒绝，零数据返回 |

同一个尾号在两个租户下返回不同客户，证明**租户隔离生效**。

### 2.3 对话上下文隔离

```bash
openclaw config set session.dmScope per-account-channel-peer
```

每个微信 peer 独立 session，用户 A 的对话不会影响用户 B。

## 三、服务器部署架构

```text
微信用户 A / B / C ...
        │
        ▼
微信服务器（腾讯）
        │  @tencent-weixin/openclaw-weixin 插件
        ▼
OpenClaw Gateway（服务器，:18789）
        │
        ▼
店脑微信网关（服务器，:7402）
        │  sender → 店脑账号 映射，每用户独立 token
        ▼
店脑业务 API（服务器，:7401）
        │  租户隔离 · 角色权限 · 审计 · 幂等
        ▼
PostgreSQL（tenant_id 行级隔离）
```

## 四、服务器部署必须补的四件事

| # | 事项 | 现状 | 要做 |
|---|---|---|---|
| 1 | 微信登录态 | 本机扫码 | 在服务器上扫码（或迁移 `~/.openclaw/openclaw-weixin` 凭证），个人号有封号风险 |
| 2 | HTTPS / 反向代理 | 本地明文 HTTP | Nginx/Caddy + 证书，API 不暴露公网明文 |
| 3 | 进程守护 | 手动/批处理 | pm2 或 systemd，开机自启、崩溃重启 |
| 4 | 数据库 | 内存 store | 切 PostgreSQL，迁移脚本 `db/migrations/0001–0007` 已备 |

### 参考部署命令（Linux 服务器）

```bash
# 1. 安装 Node 24.16+（OpenClaw 要求）
# 2. 部署代码
cd /opt/diannao && npm install && npm run build:api

# 3. 进程守护
pm2 start dist/services/api/src/server.js --name diannao-api
pm2 start adapters/wechat/gateway.mjs --name diannao-wechat-gw
cd runtime/openclaw && pm2 start "node --env-file=.env node_modules/openclaw/openclaw.mjs gateway run" --name diannao-clawbot
pm2 save && pm2 startup

# 4. Nginx 反代（只暴露必要的入口）
# /v1/*      → 127.0.0.1:7401
# /wechat/*  → 127.0.0.1:7402
# 18789 不对外暴露
```

## 五、多用户还缺的产品能力

当前是「演示级多用户」，正式对外服务还差：

1. **绑定码机制**：现在 `users.json` 里是明文密码（演示账号）。正式应改为：店长在网页生成一次性绑定码 → 店员在微信发送绑定码 → 服务端写绑定关系。
2. **限流与计费**：按租户/席位/调用量限额，防止一个租户打爆服务。
3. **每租户的机器人策略**：一个微信号服务多家店，还是每家店一个号？个人号方案后者更安全但成本高。
4. **数据隔离审计**：定期抽查跨租户访问日志，确保 0 越权。

## 六、限制与风险（必须知道）

| 风险 | 说明 | 建议 |
|---|---|---|
| 个人微信号封号 | 腾讯对非官方机器人有封禁风险 | 试点可用；正式商用换企业微信/公众号 |
| 单号多商户 | 一个机器人混服务多个商家，消息量与身份易混 | 每店一个机器人号，或按租户分渠道 |
| 微信登录态迁移 | 扫码依赖手机与网络环境 | 服务器首次部署需人工扫码一次 |
| 成本 | DeepSeek 按 token 计费，多用户线性增长 | 加限流与用量统计 |

## 七、本机现在的状态

- 微信网关：多用户模式，3 个绑定用户
- OpenClaw：DeepSeek Chat，session 按 peer 隔离
- 店脑 API：租户隔离 + 角色权限
- 已验证：同尾号跨租户返回不同客户，未绑定用户被拒

**离「服务器多用户」还差的是部署工程，不是架构。**
