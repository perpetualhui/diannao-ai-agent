# 店脑 · 容量评估与多用户说明

日期：2026-11-07｜服务器：43.155.155.230（Ubuntu 24.04 / 3.6G 内存 / 59G 磁盘）

## 一、当前部署实测

| 组件 | 进程 | 内存 | 说明 |
|---|---|---|---|
| 店脑 API | diannao-api | ~65MB | Node 单进程，内存数据 |
| 微信网关 | diannao-wechat-gw | ~70MB | sender → 账号映射 |
| OpenClaw ClawBot | diannao-clawbot | ~538MB | 含微信插件与模型客户端 |
| Nginx | 系统服务 | ~20MB | HTTPS 反代 |
| 系统 + 其他 | — | ~400MB | |
| **合计** | | **~1.1–1.3G** | 剩余 ~2.3G |

## 二、瓶颈在哪（按严重程度排序）

| # | 瓶颈 | 现状 | 影响 |
|---|---|---|---|
| 1 | **微信账号是单点** | 一个个人微信号（7a0ab47d45d0-im-bot）服务所有用户 | 好友数、消息频率、风控都受这一个号限制 |
| 2 | **模型调用速率** | DeepSeek API 按账号 tier 限流 | 并发对话会排队，高峰响应变慢 |
| 3 | **内存数据** | API 用内存存储，重启重置 | 不能直接上生产，需切 PostgreSQL |
| 4 | API 单进程 | Node 单线程 | 轻查询不是瓶颈（QPS 数百），但 AI 长任务会占住事件循环 |

## 三、能支持多少用户（务实估算）

### 场景 A：当前形态（一个微信机器人 + 多用户绑定）

| 指标 | 估算 | 依据 |
|---|---|---|
| 可绑定微信用户 | **50–100 人** | users.json 无上限；受微信好友数与消息频率制约 |
| 同时在线对话 | **10–20 人** | DeepSeek 速率 + 单 agent 处理 |
| 每日消息量 | **数千条** | 个人号风控阈值内 |
| 可承载门店（租户） | **10–20 家** | API 层面无压力，瓶颈在"一个号服务多店"的体验 |

### 场景 B：商用形态（每店一个机器人号 + PostgreSQL）

| 指标 | 估算 | 前提 |
|---|---|---|
| 每店用户 | 5–20 人 | 单店规模 |
| 门店总数 | **100+** | 每个门店独立微信/企业微信账号 |
| 并发 | 按模型配额扩展 | 加限流 + 队列 |

## 四、结论

**当前这台 4G 服务器，足够支撑 10–20 家门店、50–100 个绑定用户的演示与小规模试点。**

真正商用前必须补三件事：
1. **每店独立机器人账号**（或企业微信），避免一个个人号服务多家店
2. **切 PostgreSQL**（迁移脚本已备），否则重启丢数据
3. **加限流与用量统计**，防止单租户打爆模型配额

## 五、扩容路径

```text
现在：4G 单机 + 个人号 + 内存
  ↓ 试点期（10-20 店）
4G 单机 + 多机器人号 + PostgreSQL
  ↓ 成长期（50-100 店）
8G 双机 + 消息队列 + 独立 AI 服务
  ↓ 规模化（100+ 店）
K8s/容器 + 多租户隔离 + 按租户限流计费
```
