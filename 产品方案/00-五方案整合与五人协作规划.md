# 店脑：五方案整合与五人协作规划

版本：v1.0｜日期：2026-11-07｜性质：整合建议与开工基线，尚不代表功能已开发或通过试点。

依据：用户提供的《产品方案FInal》五份草案，以及本次明确提出的 CLAUDE.md、ROADMAP.md、README.md 文档规范。原文中“已确认”“已实测”属于原草案表述；缺少证据的事项在此仍列为待验证。

## 1. 五份方案合起来，做什么产品

**建议统一为“店脑：门店经验与老客服务系统”。先用母婴店跑通一个完整业务闭环，把老员工脑中的客户记忆变成门店可交接、可查询、可追溯的资料；防诈保留一个可选的隔离小流程，微信作为共享后台的可选聊天入口。**

首版要回答的核心问题是：老店员离开后，新店员能否在接待时找到正确客户，知道上次买了什么、有哪些偏好、哪些信息还需确认，并把这次服务继续记下来？

| 原方案 | 最有价值的部分 | 合并后的落点 |
|---|---|---|
| ① 母婴店 AI 客户运营系统·产品方案 | 真实门店痛点；先垂直试点；客户、商品、消费联动；分阶段上线 | 以母婴为首发，用真实门店验证交接价值；保留基础商品与消费记录，不把全自动触达当作首版前提 |
| ② 店脑·统一架构产品方案 | 客户与服务对象分离；认人、推荐、提醒机制分开；来源追踪；行业配置复用 | 客户与孩子分别建模；身份由检索确认、推荐由规则筛选、AI组织表达；行业差异集中配置 |
| ③ 功能主干规格 | 客户、商品、销售、AI、运营后台等模块划分清楚；通用字段加行业扩展 | 作为开发模块拆分依据；首版只做基础统计、推荐草稿和待办，后续再做预测与复杂运营 |
| ④ 产品需求文档 | 多商家隔离；身份歧义处理；经验审核；事实与经验分开；回答可追溯 | 作为数据权限、知识审核和回答质量的底线；网页与微信共用同一后端 |
| ⑤ 黑客松／老客记忆方案（含 v3 补充） | 导出导入冷启动；三步录入；三行提示；数据归店；官方反诈案例；公共提示词复用 | 作为使用体验和试点落地方法；建立来源、导出、撤权机制；反诈案例独立审核与检索 |

五份方案的优势分别是：**①确定先解决什么，②确定公共机制，③确定模块边界，④保证可信可控，⑤保证门店用得起来。**

### 冲突的统一处理

| 分歧 | 本版建议 | 原因与限制 |
|---|---|---|
| 母婴优先，还是多个行业一起做 | 母婴完成闭环；服装、汽修各保留字段配置样例，后续只选一个行业实测 | 首日预留配置边界，不承诺所有行业永远只改配置、不改代码 |
| 防诈远期再做，还是首版就做 | 放入隔离的受控演示流程，复用检索、引用、审核能力；正式公众服务另行验收 | 防诈不是药店促销的附属功能，也不能检索商家私有资料 |
| 微信插件优先，还是企微优先 | 按第五份方案优先验证微信插件文本通道；网页业务独立可用，企微只保留适配空间 | 插件型号、接口和身份机制未核实，不承诺已支持图片、语音、名片、群聊或历史导出 |
| 先做通用平台，还是先做单店 | 一个代码库、清晰业务表、母婴配置包；第二行业验证后再抽象 | 避免一开始搭建过大的通用实体平台 |
| 99／299 元定价，还是价格待定 | 先记录订阅意向、愿付金额、实际使用成本，价格保持待定 | 原文价格不是经过试点验证的商业结论 |

## 2. 第一件事：统一配置和文档

### 2.1 每个层级只维护一份规则正文

采用你的约定：团队以 Claude Code 为主，**CLAUDE.md 是全局及项目协作规范的唯一正文，AGENTS.md 只做一句话入口。**

注意路径拼写：Claude Code 是 `~/.claude/CLAUDE.md`，不是 `~/.cladue/CLAUDE.md`。Codex 默认全局指令文件为 `~/.codex/AGENTS.md`；如果成员设置了 `CODEX_HOME`，应使用其实际目录。[Claude Code 官方说明](https://code.claude.com/docs/en/memory)、[OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

```text
成员电脑：
~/.claude/CLAUDE.md     全局通用协作规范正文
~/.codex/AGENTS.md      一句话：要求读取全局和项目 CLAUDE.md

项目仓库根目录：
CLAUDE.md              项目定义、功能、架构、技术栈、开发与验收规则
AGENTS.md              一句话：要求读取全局和项目 CLAUDE.md
ROADMAP.md             当前进度、下一步、负责人、阻塞、验收证据
README.md              面向店主和店员的使用说明
```

两个 AGENTS.md 都可以只写以下同一句，不再复制任何规范条款：

> 请在开始工作前读取并遵循 `~/.claude/CLAUDE.md` 和当前项目根目录的 `CLAUDE.md`，全局与项目协作规范分别以对应文件为准。

这属于明确的读取指令，不等于 Codex 原生自动发现 CLAUDE.md。初始化后分别开一个 CC、Codex 会话，检查它们能列出两个文件路径并复述本项目范围；若存在优先加载的 `AGENTS.override.md`，先核对是否遮蔽入口。[OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

“一份”指全局一份正文、每个项目一份正文。五个人电脑上的全局文件不会自动同步：由 B 维护团队全局模板版本，五人安装同一版本；项目文件通过 Git 同步。此处统一的是 AI 协作指令，工具账号、密钥与各工具运行设置仍按各自方式管理。

### 2.2 三份项目文档各管一件事

| 文件 | 必须回答的问题 | 维护责任 | 更新时机 |
|---|---|---|---|
| CLAUDE.md | 产品是什么？当前版本边界？用什么技术？目录与接口如何分工？什么规则不能破坏？ | B 主维护；A确认范围，D确认AI规则，相关负责人提交变更 | 架构、接口、技术栈、范围或工程规则变化时 |
| ROADMAP.md | 现在做到哪？谁在做？下一步是什么？卡在哪里？完成证据是什么？ | A 统筹；每人更新自己任务行 | 领任务、发现阻塞、提交验收、完成时 |
| README.md | 人怎么登录、导入、查询、录入、审核、导出？遇到问题怎么办？ | C 主维护；A核对业务，E核对实际可用性 | 用户可见功能或操作流程变化时 |

本项目面向外部门店，README.md 从第一版就保留。三份文档中不重复维护同一份任务清单：进度只放 ROADMAP，工程规则只放 CLAUDE，用户操作只放 README。详细接口与数据结构优先从代码契约和迁移文件读取；文档只描述原则、入口和必要示例。

**状态必须真实：**“写好方案”“页面能演示”“接口接通”“完整流程验收通过”“真实门店用过”是不同状态，不能都标为完成。文档模板目前均标注尚未开发／尚未验收。

## 3. 首版产品范围与完整流程

### 3.1 首版必做的闭环

1. 店主建立门店空间，给店员分配账号与权限。
2. 导入现有客户、商品及历史购买资料；字段映射、错误行和重复项可查看，导入前先预览。
3. 整理老员工经验：输入文字，AI 提取为待确认草稿，店主审核后可检索。
4. 新店员按会员号、姓名或手机尾号寻找客户；重名、重尾号先确认身份。
5. 客户卡片展示历史事实、已审核经验和待确认信息，默认给三行服务提示，来源可展开。
6. 店员完成服务后，在“识别对象→填写／采集→确认提交”三步内补录关键记录。
7. 店员确认本次服务结果并保存；推荐草稿、规则待办和基础统计按P1开关逐步加入。
8. 老员工离职后撤销访问权限，客户记录和已审核经验继续保留在门店；授权管理员可导出。

示例：客户说“和上次一样”。系统先确认客户及本次服务的孩子，查出上次具体 SKU、规格、购买时间和货架位置，生成提示；查不到则说明缺资料，不能自行猜商品。新购买经店员确认后再写入记录。

### 3.2 首版功能优先级

| 级别 | 范围 | 交付要求 |
|---|---|---|
| P0：正式内测必须完成 | 登录与权限、门店隔离、客户及孩子资料、商品及购买记录、CSV导入、经验审核、搜索与带来源问答、服务回写、审计与管理员导出、手机网页 | 无需微信即可完成完整接待与交接流程；Excel先转换CSV，有样本后再决定直接支持xlsx |
| P1：本轮争取完成，可独立开关 | 推荐草稿、规则待办、基础销售统计、微信文本查询及身份绑定、隔离的反诈演示 | 不阻塞P0；任何待验证能力在演示中明确标识 |
| P2：后续 | 语音／图片自动采集、聊天历史导入、自动触达、多店经营、更多行业完整流程、预测补货、收费系统 | 依据试点证据另排期 |
| 暂不做 | 3D货架、自动医疗建议、AI自行改交易、无审核事实入库、未经验证的诈骗定性 | 保持首版范围和证据要求清楚 |

反诈演示只验证“输入描述→检索已审核案例→显示匹配信号、来源、不确定项→必要时转人工”。案例先由 A 收集官方资料、D 整理并交 A 审核；没有审核通过的来源时，不编造案例，也不把未命中理解为安全。本轮不直接照搬原文的“七项打分”或声称识别准确率。

### 3.3 明确修正原方案的薄弱处

- 客户使用独立 `customer_id`，所有查询带服务端确认的 `tenant_id`；手机尾号只是搜索条件，不能当主键。即使增加姓名，也不替代系统ID。
- 家长与孩子分开建模，支持一位家长多个孩子；出生日期明确时动态计算月龄，不完整时保留未知或精度说明。
- 客户事实、通用经验、模型推测分别保存和展示；模型提取先形成草稿，未经人工确认不覆盖事实。
- 价格、库存、适用范围以已审核且注明时间的商品资料为依据。信息过期或冲突时提示核对，不能承诺实时库存。
- 同一事实冲突时保留来源和历史，交人工处理；涉及禁忌的冲突先阻止相关自动推荐。
- 店员默认没有批量导出权限；管理员按授权范围导出并留审计。
- 不继承“企微不封号”“几个账号测试就能推算封号率”等未经支持的承诺；渠道故障回到网页与人工流程。

## 4. 共用架构与协作接口

### 4.1 建议技术基线

沿用原方案的主要选型方向：Vue 3＋TypeScript＋Element Plus 负责网页，PostgreSQL／Supabase 承载数据和认证，统一服务端 API 处理权限、检索、规则与模型调用。选择单一模型供应商完成首轮验收，模型供应商和微信插件通过适配器隔离。

以上是建议开发基线；具体版本、部署地域、账号能力、费用和真实门店访问条件，由 B、E 在第1周验证并记录。不沿用原文“免费档一定够用”的结论。

```text
网页入口 ───────────┐
微信文本适配器 ──────┼→ 身份认证与数据权限 → 统一业务服务
导入工具 ───────────┘                      │
                      ┌───────────────────┼─────────────────┐
                      客户/商品/记录       审核知识与检索      规则与待办
                      └───────────────────┼─────────────────┘
                                          ↓
                                 AI组织回答与来源校验
                                          ↓
                                人工确认、回写、审计

反诈公开案例：使用独立的检索范围与入口权限，不连接门店客户资料。
```

采用一个仓库、一个主要服务端部署和一个数据库起步。建议代码区域为 `apps/web`、`services/api`、`services/ai`、`adapters/wechat`、`packages/contracts`、`db/migrations`、`configs/scenarios`、`tests/e2e`。`services/ai`先作为同一服务端部署内的独立模块，不要求单独搭建微服务。这些是拟建目录，不代表现有仓库已具备代码。

### 4.2 第1周必须共同固定的契约

| 契约 | 统一内容 | 主责与协作 |
|---|---|---|
| 身份与权限 | tenant_id、user_id、role、customer_id、subject_id；服务端从登录态解析租户与权限；前端和微信不能自行指定可信租户 | B 定义，C／D／E共同使用 |
| 记录与来源 | record_id、source_type、source_id、actor_id、occurred_at、created_at、review_status；来源继承同一数据权限 | B＋D |
| 客户匹配 | 返回状态：matched／ambiguous／not_found；歧义只返回授权的脱敏候选，不直接暴露完整档案 | B 定义，C／E展示，D不得猜身份 |
| 问答结果 | subject、facts、approved_experience、suggestions、citations、uncertainties、handoff_required；每条具体事实关联来源ID | D 定义，B核对授权，C／E展示 |
| 知识状态 | draft→pending_review→approved→archived；只有approved进入正式检索；下架同步失效检索索引／缓存 | D＋B，C提供审核界面 |
| 服务回写 | 确认用户、权限、目标对象、输入校验、幂等键；失败不显示成功 | B 定义，C／E调用 |
| 消息与任务 | message_id／task_id、状态、重试规则、幂等键；首次接入只支持已实测的文本能力 | E＋B；D只接收归一化输入 |
| 数据导入 | source_file、row_number、字段映射、预览、错误原因、去重依据、批次ID；重复执行不重复记账 | B实现，A给样本，C做导入流程 |

最先固定五个接口操作：查找客户、获取授权客户摘要、提交服务记录、提交经验草稿／审核、执行授权问答。端点和类型定义由 B、D 在仓库契约文件中确定，其他人据此开发和使用 Mock，避免每个模块各定义一套客户字段。

| E：渠道与质量负责人 | 微信插件能力验证、身份绑定、消息适配与幂等、持续集成、端到端测试、部署、日志、备份恢复 | 插件能力矩阵、可复现联调记录、测试报告、试点环境、恢复演练、发布检查记录 | 更新ROADMAP验证状态；补充README故障处理 | B复核渠道鉴权；C复核跨端结果 |

**工作量处理：**A同时承担数据准备、知识内容和真人验收，不能只主持会议；E从第1天就建设环境和测试，不能等最后验收。B负责共享基础，但D独立实现AI服务、E独立实现适配器，避免所有接口实现都排队等B。

**每项任务一个主责、一个复核人。**共同负责某个模块时仍要拆成可验收子任务。五个人共做同一条闭环，新增行业作为配置与后续验证任务安排。

### 一条功能的协作示例

“查询尾号1234的客户上次买过什么”：A提供真实问题和标准答案→B定义候选检索与记录接口→C做歧义选择和客户卡片→D根据授权记录生成带来源摘要→E验证网页与微信得到一致结果，并加入重尾号、越权、无记录回归用例→A验收后更新状态。

## 6. 四周推进计划

## 7. 每天怎样合力推进

### 7.1 任务粒度和同步节奏

每张任务卡控制在约半天至两天可交付，包含：任务ID、用户结果、负责人、复核人、输入依赖、允许修改的模块、验收步骤、证据位置、状态。大任务先拆分，避免一周后才发现接口不兼容。

每日10分钟同步只说：昨天完成并验证了什么、今天交付什么、被谁／什么阻塞。建议每周至少两次把各分支集成到测试环境，直接演示一条接待链路。遇到阻塞当天写入 ROADMAP，依赖方仍可使用已约定的 Mock 推进。

### 7.2 Git与AI协作约定

1. 每人使用自己的分支和工作目录；同时使用多个AI时采用独立worktree或独立克隆，避免同一目录被同时修改。
2. 开始前让AI读取全局CLAUDE、项目CLAUDE和ROADMAP中当前任务；说明任务ID、边界、依赖和验收步骤。
3. 共享契约、数据库迁移和根级CLAUDE由B协调合并，功能负责人负责提出修改与实现；涉及用户范围由A确认。
4. 小步提交，提交PR时说明用户行为变化、验证结果、对应文档变更；作者不能独自判定完成。
5. 同一PR更新必要文档：改变功能同步README，改变规则同步CLAUDE，改变状态同步ROADMAP。没有相关变化就不为形式重复改三份。
6. ROADMAP由每人修改自己任务行，A汇总当前里程碑；同时改同一部分时协调顺序，合并冲突逐项核对。
7. AI不能把猜测写成已验证结论，也不能把未运行测试写成通过。任务必须附可复现步骤或证据。

给AI的任务示例：

```text
先读取全局CLAUDE.md、项目CLAUDE.md和ROADMAP.md中的WEB-02。
实现“尾号重复时先选客户，再展示历史记录”。
仅修改apps/web下相关页面；接口遵循packages/contracts。
验收：单匹配、双匹配、无匹配三种情况；未确认前不出现完整客户档案。
完成后说明实际验证结果，并更新WEB-02；不要把尚未联调的接口标为完成。
```

## 8. 怎么判断做完了

以下为建议验收标准，尚无实测结果；开工时由A、B、E确认测试环境、数据集与样本，之后保持口径一致。渠道与防诈两项仅在启用对应P1功能时适用；未启用不阻塞P0网页试点，但不能标为已支持。

| 类别 | 可检查的验收条件 | 验收负责人 |
|---|---|---|
| 权限 | 两个测试商家互相不能读取客户、经验、来源或导出；公开反诈入口无法读取门店数据；撤权店员旧会话也失去查询能力 | E主测，B修复 |
| 客户识别 | 重名、重尾号、无匹配、一客多孩子都走正确分支；歧义未确认时不展示完整档案 | A＋E |
| 导入与回写 | 有效行成功、错误行有原因；预览与结果一致；重复导入／请求不产生重复交易；失败不显示成功 | E＋B |
| 知识生命周期 | 草稿不可用于正式回答；批准后可检索；下架后从检索和相关缓存中失效，历史审计仍在 | A＋D＋E |
| 回答可核对 | 建议先做30条固定问题集，包含有答案、缺资料、冲突、重名、越权；检查每条具体事实是否有授权且能支持结论的来源；关键编造或泄漏未修复前不得发布 | A标注，D评测，E复核 |
| 使用体验 | 建议邀请3名未参与开发的试用者，每人独立完成找客户、看上次购买、补服务、查依据4项任务；目标至少10／12项无需开发者帮助完成，失败点逐条记录 | A＋C |
| 速度 | 记录客户查询和AI回答的p50／p95及测试条件；建议普通查询p95≤2秒、AI完整回答p95≤10秒，在约定试点并发下测量 | E；阈值可按真实条件调整 |
| 渠道 | 只有通过身份绑定、文本往返、重复事件去重和断连恢复测试的插件能力才标“已支持”；未通过则保留网页试点 | E＋B |
| 防诈演示 | 使用已审核的官方来源，输出依据和不确定项；无命中不判安全；不对具体对象作确定性诈骗定性 | A＋D |
| 交接与恢复 | 第二位成员按文档启动／进入测试环境完成接待流程；在隔离环境从备份恢复并核对关键记录 | E组织，另一成员执行 |

商业价值先看实际行为：新店员查到资料耗时、服务后记录完成比例、店主是否持续使用、客户资料覆盖程度。可以观察试点前后变化，但短期少量门店的数据不能直接证明增收或归因到AI。
